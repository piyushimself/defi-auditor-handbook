What an auditor actually does
  1. Understand how the system should work and who is trusted.
  2. Write the rules (invariants) that must never break.
  3. Read the code looking for any way to break a rule.
  4. Prove it with a working test (a proof of concept).
  5. Report it with a fix.

Almost every real hack is one of a small number of patterns: a manipulated price, bad rounding, a missing check, a trusted-but-wrong input, or a stolen key. This book is organized to make you fast at recognizing them.

Your first bug (15 minutes, do it now)

This bank has a classic flaw. Find it before reading on.

contract Bank {
    mapping(address => uint256) public balance;
    function deposit() external payable { balance[msg.sender] += msg.value; }
    function withdraw() external {
        uint256 amt = balance[msg.sender];
        (bool ok, ) = msg.sender.call{value: amt}("");   // sends ETH first
        require(ok);
        balance[msg.sender] = 0;                          // updates balance last
    }
}

The bug: it pays before it zeroes the balance. An attacker's contract receives the ETH, and in its receive() function calls withdraw() again while the balance is still non-zero, draining the bank. This is reentrancy, the bug behind The DAO hack. Fix: set balance[msg.sender] = 0 before the external call (the checks-effects-interactions pattern), or add a reentrancy lock. Write the attacker contract in Foundry as your first PoC.

1. Foundations (do not skip)

In plain English: The shared toolkit. Every later bug is some way of breaking an assumption taught here: how the EVM behaves, how tokens misbehave, how math rounds, how signatures and oracles can be abused.

1.1 The audit workflow in detail
  1. Scope & docs: read specs, diagrams, prior audits, known issues. List what is out of scope.
  2. Build the threat model: actors (users, LPs, keepers, admins, oracles, bridges), assets (what can be stolen/frozen), trust assumptions (who is trusted to do what).
  3. Map the code: entry points (external/public), privileged functions, external calls, state variables that hold value, invariants.
  4. Automated pass: Slither, Aderyn, forge build --sizes, forge coverage. Triage noise, keep leads.
  5. Manual line-by-line pass on value-moving functions first: deposit, withdraw, swap, borrow, liquidate, harvest, claim, upgrade.
  6. Invariants and fuzzing: Foundry invariants, Echidna/Medusa, Halmos for narrow symbolic proofs.
  7. PoC and severity: impact x likelihood, with assumptions stated. Provide a fix.
  8. Report: title, root cause, impact, PoC, recommendation. One bug per finding.
1.2 EVM facts every auditor must know cold
  • Storage: slots are 32 bytes; mappings at keccak256(key . slot); dynamic arrays at keccak256(slot); packed variables share slots; ERC-1967 proxy slots are hashes minus one.
  • Calls: call (new context, new msg.sender), delegatecall (caller's storage, preserves msg.sender), staticcall (no state change), low-level call returns success flag that must be checked.
  • Return data: address.call to a non-contract succeeds. extcodesize is zero during construction and for to-be-created addresses.
  • Gas: 63/64 rule on forwarded gas; transfer/send forward 2300 gas and can break with contract recipients; unbounded loops are a DoS vector.
  • Transient storage (EIP-1153, Cancun): tload/tstore cleared per transaction; used for cheap reentrancy locks and flash accounting (Uniswap v4). Danger: lock not reset in same tx where multiple calls happen, or composability with delegatecall.
  • Selfdestruct (post-Dencun, EIP-6780): only deletes if created in same tx. Can still force-send ETH to any contract, so never rely on address(this).balance equality.
  • Create2: deterministic addresses; metamorphic contracts are mostly dead after EIP-6780 but still read about them.
  • Solidity 0.8: checked arithmetic by default; unchecked blocks are a risk; narrowing casts silently truncate (uint128(x)); abi.encodePacked with dynamic types collides.

1.4 Math, precision and rounding
  • Fixed-point: WAD (1e18), RAY (1e27), Q64.96 (Uniswap v3 sqrtPrice), Q112 (v2 TWAP). Mixing scales is a bug factory.
  • Rounding rule: round in favor of the protocol, against the user. Shares minted: round down. Assets owed to user: round down. Assets the user must pay: round up. Debt computed: round up.
  • Divide last: a * b / c, not a / c * b. Use mulDiv to avoid phantom overflow (Math.mulDiv, Solady FixedPointMathLib).
  • Dust and zero: shares can round to zero; zero-share deposits steal; 1-wei donations break ratios.
  • Casting: int256(uint256) large values wrap; uint96/uint128 packing overflows silently on cast.
  • Precision loss across multiple operations compounds (interest per block vs per second).
1.5 Reentrancy, fully
  • Classic: external call before state update.
  • Cross-function: two functions share state; attacker re-enters the other one.
  • Cross-contract: protocol A calls B; B reads A's inconsistent mid-state.
  • Read-only: a view function reads state mid-update; the integrator trusts it (Curve get_virtual_price during remove_liquidity, Balancer pools).
  • Token-hook reentrancy: ERC-777 tokensReceived, ERC-721 onERC721Received, ERC-1155 callbacks, ETH receive.
  • Defenses: checks-effects-interactions, nonReentrant (and make it cover view-reading integrators via a nonReentrantView check), pull payments, transient locks.
1.6 Access control, upgradeability, governance
  • Initializers: initializer modifier, uninitialized implementation takeover (UUPS: upgradeToAndCall to a selfdestruct-capable contract in pre-Dencun days; Wormhole's uninitialized implementation bounty 2022 is a famous near-miss).
  • Storage layout collisions across upgrades; use storage gaps or namespaced (ERC-7201) storage.
  • Role design: who can grant roles? Is there a timelock? Is the admin an EOA, multisig or governance?
  • Flash-loan governance (Beanstalk, Apr 2022, ~$180M): borrowed voting power plus emergency-execute path let attacker pass a malicious proposal in one transaction.
  • Always ask: can an admin steal funds? If yes, that is a centralization finding at a severity that depends on the contest/audit rules.
1.7 Oracles
  • Chainlink consumer checks: answer > 0; updatedAt within heartbeat + buffer; answeredInRound >= roundId (deprecated pattern but still seen); min/max aggregator bounds (LUNA incident: price clamped at floor); decimals (8 vs 18); L2 sequencer uptime feed with a grace period.
  • Uniswap TWAP: cost to manipulate rises with window length and liquidity; short windows on thin pools are attackable; multi-block MEV makes it cheaper post-Merge for block builders.
  • Pull oracles (Pyth, Redstone): confidence interval, publish time, update fee, who submits the update (attacker chooses among valid prices).
  • Composite/LP-token pricing: value LP tokens using fair-pricing formulas (Alpha Homora fair LP price), not spot reserves.
1.8 Signatures

ECDSA malleability (s upper half), ecrecover returning zero address, replay across chains/contracts (EIP-712 domain separator with chainId and verifyingContract), missing nonce/deadline, signing over incomplete data (arbitrary calldata smuggling), ERC-1271 for contract wallets (return magic value check), permit front-running griefing (permit consumed by attacker causes subsequent permit call in your contract to revert).

1.9 Economic attack primitives

Flash loan; donation / direct transfer to change ratios; sandwich; oracle manipulation; just-in-time liquidity; liquidation griefing; first-depositor attack; governance flash-vote; sybil; dust attack. Almost every DeFi exploit is one or two of these plus a missing check.

1.11 Foundry invariant test skeleton (reuse everywhere)
// test/invariant/Handler.t.sol
contract Handler is Test {
    Vault public vault;
    IERC20 public asset;
    address[] public actors;
    uint256 public ghostDeposited;
    uint256 public ghostWithdrawn;

    constructor(Vault v) { vault = v; asset = IERC20(v.asset()); /* seed actors */ }

    function deposit(uint256 actorSeed, uint256 amt) external {
        address a = actors[actorSeed % actors.length];
        amt = bound(amt, 1, 1e24);
        deal(address(asset), a, amt);
        vm.startPrank(a);
        asset.approve(address(vault), amt);
        vault.deposit(amt, a);
        vm.stopPrank();
        ghostDeposited += amt;
    }
    // withdraw(), donate(), warp(), setPrice() ... bound everything
}

contract VaultInvariants is Test {
    Vault vault; Handler h;
    function setUp() public {
        vault = new Vault(/*...*/);
        h = new Handler(vault);
        targetContract(address(h));
    }
    function invariant_solvency() public view {
        assertGe(asset.balanceOf(address(vault)) + h.ghostWithdrawn(), h.ghostDeposited());
    }
}

Rule: the handler should be able to do everything a hostile user, a donor, a keeper and time can do.

2. DEXesorig #4

In plain English: A vending machine for swapping tokens whose price comes from a formula, not a person. If an attacker can move the formula's inputs, they control the price, and anything that trusts that price.

Difficulty ●●●○○Time ~2 weeksNeeds: Ch 1

Primary lenses: Order & Control Flow, Adversary Thinking, Value Flow.

2.1 Why it matters

AMMs are the price oracle of crypto and the main target of flash-loan manipulation. Their math is the template for lending collateral pricing, vault share math and derivatives index prices.

2.2 Prerequisites

Foundations 1.3 to 1.5, 1.7. Comfortable with sqrt and fixed-point math.

2.3 Core mechanics

Constant product (Uniswap V2): x * y = k.

  • Swap in dx with fee f (0.3% = 997/1000): dy = y * dx * 997 / (x * 1000 + dx * 997).
  • Price impact grows with dx / x. A trade of 1% of reserves moves price about 2%.
  • LP mint: first deposit mints sqrt(x*y) - MINIMUM_LIQUIDITY (1000 wei locked forever); later min(dx * S / x, dy * S / y). Burn returns proportional reserves.
  • Fees accumulate in reserves (k grows); feeTo mints protocol shares (1/6 of growth when on).
  • TWAP: price0CumulativeLast += price0 * timeElapsed, in UQ112x112, updated once per block on first interaction.
  • Functions to know: sync(), skim(), flash swaps (callback and k-check after).

Concentrated liquidity (V3):

  • Liquidity L = sqrt(x*y) within a range [Pa, Pb]. Price represented as sqrtPriceX96 = sqrt(P) * 2^96.
  • Ticks: price = 1.0001^tick; tickSpacing depends on fee tier. Active liquidity changes as price crosses initialized ticks (liquidityNet).
  • Per-position fee accounting via feeGrowthGlobal, feeGrowthOutside, feeGrowthInside (underflow is intentional/unchecked).
  • Oracle: ring buffer of observations; observe() with tick cumulative (geometric mean TWAP).

Uniswap V4: singleton PoolManager, hooks (arbitrary contract logic around swaps/liquidity), flash accounting with transient storage and unlock callback, native ETH support, custom accounting. New attack surface: hook permissions encoded in address bits, hooks that change swap deltas, reentrancy into the manager, hook trusting msg.sender.

StableSwap (Curve): invariant A*n^n*Σx + D = A*D*n^n + D^(n+1)/(n^n * Πx). Behaves like constant sum near balance and constant product when imbalanced. D is solved by Newton's method (loops, rounding, convergence). get_virtual_price = D / totalSupply (should only increase). Meta pools, rebasing tokens, ETH pools (callbacks on raw_call).

Balancer: weighted pools Π balance_i^w_i = k; vault holds all tokens; flash loans free; read-only reentrancy via Vault getPoolTokens/BPT price during join/exit.

Order-book/intent DEXes (CoW, UniswapX, 1inch Fusion): signed orders, solver competition, batch auctions; bugs are in signature validation, settlement accounting, and solver griefing.

2.5 Invariants (write these as tests)
  • k after swap >= k before swap (fees only increase it).
  • Sum of LP shares * reserve share == reserves; no one can redeem more than they own.
  • Swap output is monotonic in input and never exceeds reserves.
  • Price and TWAP stay within a bound over a short window absent huge capital.
  • After mint then immediate burn, user gets back at most what they put in.
  • Protocol fees collected never exceed accrued fees.

3. Lendingorig #2

In plain English: A pawn shop run by code: lock collateral, borrow against it, get liquidated if the collateral value falls. Bugs come from wrong prices, wrong bookkeeping, and liquidations that do not work when needed.

Difficulty ●●●○○Time ~2 weeksNeeds: Ch 1, 2

Primary lenses: Value Flow, Time, Failure Modes, Assumptions.

3.1 Why it matters

Lending protocols hold the largest TVL in DeFi and every liquidation path is an adversarial game with oracles, gas, and market liquidity.

3.2 Core mechanics

Pool-based (Compound, Aave): suppliers deposit and receive receipt tokens (cTokens/aTokens); borrowers post collateral and borrow against it; rates are set by utilization U = borrows / (cash + borrows - reserves).

Interest rate model (kinked):

  • Below optimal utilization: rate = base + slope1 * U/U_opt.
  • Above: rate = base + slope1 + slope2 * (U - U_opt)/(1 - U_opt).
  • Reserve factor: portion of interest goes to reserves.

Indexes: instead of updating every user each block, protocol stores a global borrowIndex and supplyIndex that grow with compounding; user debt = principal * currentIndex / userIndex. Interest must be accrued before any state-changing action.

Risk parameters: loan-to-value (LTV, max initial borrow), liquidation threshold (LT), liquidation bonus/penalty, close factor (portion repayable per liquidation), supply/borrow caps, isolation mode, e-mode (correlated assets), reserve factor.

Health factor (Aave): HF = Σ(collateral_i * price_i * LT_i) / Σ(debt_j * price_j). HF < 1 means liquidatable.

Liquidation: liquidator repays part of debt, seizes collateral at a discount. Profitability needs: bonus > gas + slippage + oracle lag. If not, positions go underwater and create bad debt.

MakerDAO / CDP model: mint a stablecoin (DAI) against collateral in vaults; stability fee; Vat accounting core, Dog/Clipper liquidations (Dutch auction), Spot oracle with delayed OSM (one-hour delay), PSM. Know rate accumulator (Jug.drip) and ink/art.

Morpho / Euler v2 / Fluid / Silo: peer-to-peer matching layers, modular isolated markets, vault-kit style architectures (EVC, ERC-4626 vaults as collateral). Note: more modularity means more integration assumptions.

Liquid-staking tokens and LP tokens as collateral introduce additional oracle/depeg risks.

3.3 Code anatomy

3.4 Invariants
  • totalBorrows <= totalSupplied (minus reserves) always.
  • Every position that is healthy after an action stays healthy through that action (health check at end).
  • Interest never decreases debt; indexes monotonic non-decreasing.
  • Sum of user balances (shares) equals total shares; assets per share only increases barring bad debt.
  • Liquidation never increases the borrower's health factor negatively beyond rules, never leaves liquidator profiting from protocol insolvency beyond bonus.
  • After full repay, no residual debt; after full withdraw, no residual collateral beyond dust.
  • Reserves + supplier claims >= cash + borrows when no bad debt.

5. Yield Aggregators and Vaultsorig #6

In plain English: Shared pools that split profits using shares. One rounding mistake lets the first depositor steal from the next. Vaults also call other protocols, so their bugs become yours.

5.1 Why it matters

Vaults compose many protocols; every bug in a protocol they use becomes theirs. The vault math itself (shares, fees, rounding) is the most-exploited small piece in DeFi.

5.2 Core mechanics

ERC-4626: asset(), totalAssets(), convertToShares/Assets, previewDeposit/Mint/Withdraw/Redeem, deposit/mint/withdraw/redeem, max*.

  • shares = assets * totalSupply / totalAssets (round down for deposit, up for mint's asset cost, withdraw's share burn; down for redeem assets).
  • Inflation/donation attack: first depositor deposits 1 wei (1 share), donates large assets directly to vault, so next depositor's assets * 1 / (1 + donation) rounds down to 0 shares. Auto-compounders: claim rewards → swap → add liquidity → restake (every swap is a sandwich target).

Other patterns: leveraged yield (looping on lending), delta-neutral (Ethena-like), Pendle (yield tokenization: PT/YT, SY wrappers, AMM with time decay), Convex/Aura boosting, strategy routers.

// Naive vault (vulnerable)
contract NaiveVault {
    IERC20 public immutable asset;
    uint256 public totalSupply;
    mapping(address => uint256) public balanceOf;

    function deposit(uint256 assets) external returns (uint256 shares) {
        uint256 ta = asset.balanceOf(address(this));
        shares = totalSupply == 0 ? assets : assets * totalSupply / ta;
        asset.transferFrom(msg.sender, address(this), assets);
        totalSupply += shares; balanceOf[msg.sender] += shares;
    }
    function redeem(uint256 shares) external returns (uint256 assets) {
        assets = shares * asset.balanceOf(address(this)) / totalSupply;
        totalSupply -= shares; balanceOf[msg.sender] -= shares;
        asset.transfer(msg.sender, assets);
    }
}
// Attack sketch (Foundry):
// 1) attacker deposits 1 wei -> 1 share
// 2) victim approves 1e18 and submits deposit(1e18)
// 3) attacker front-runs: asset.transfer(vault, 1e18)  -> ta = 1e18 + 1
// 4) victim's shares = 1e18 * 1 / (1e18 + 1) = 0, victim gets 0 shares
// 5) attacker redeems 1 share -> receives ~2e18

6. Derivatives: perpetuals, options, syntheticsorig #5

In plain English: Leveraged bets paid by a pool. A wrong price, bad timing, or margin math error can drain the pool that backs every winning trader.

Difficulty ●●●●○Time ~2 weeksNeeds: Ch 2, 3

Primary lenses: Time, Adversary Thinking, Assumptions, Failure Modes.

6.1 Why it matters

Derivatives are leverage plus oracles plus latency. A single stale price or margin bug can drain the liquidity pool backing every trader.

6.2 Core mechanics

Perpetual futures:

  • Mark price (for liquidation) vs index price (oracle spot basket). Funding rate keeps perp near index: funding = clamp(premium) + interest, paid between longs and shorts each interval.
  • Position: size, entry price, margin, leverage. uPnL = size * (mark - entry) (sign by side). Margin ratio = equity / notional. Initial margin vs maintenance margin.
  • Liquidation: if equity < maintenance margin; liquidator gets fee; insurance fund covers shortfalls; ADL (auto-deleveraging) if fund depleted.
  • Architectures:
  • Orderbook + clearing (dYdX v3/v4): off-chain/AppChain matching; margin accounts.
  • vAMM (Perpetual Protocol v1, early Drift): virtual reserves set price; no real counterparty.
  • Pool-as-counterparty (GMX v1/v2, Gains/gTrade, Jupiter perps): LPs (GLP/GM tokens, vaults) take the other side of traders; trader profit is LP loss; oracle prices drive everything.

  • Synthetix-style debt pool: stakers mint synths, share system debt; Synthetix Perps v2/v3 use Pyth + delayed/off-chain orders.

  • Open interest caps, skew scaling, price impact, borrow fees protect pool.

Options: Opyn (Gamma), Lyra/Derive, Hegic, Dopex, Premia, Panoptic (perpetual options via Uniswap v3 liquidity). Know: collateralized vaults, European/American settlement, expiry oracles, IV pricing (Black-Scholes in Solidity), collateral locking, exercise windows.

Synthetic assets: mint synth against collateral (collateral ratio, debt pool), peg via arbitrage, oracle-driven pricing, liquidation mechanisms.

7. Bridgesorig #3

In plain English: Moving value across chains by locking here and minting there. It is only as safe as whatever vouches that the lock happened: a few keys, a watcher, or a proof.

Difficulty ●●●●○Time ~2 weeksNeeds: Ch 1

Primary lenses: System Boundary, Trust & Power, Assumptions, Failure Modes.

7.1 Why it matters

Bridges concentrate value behind a single verification mechanism. They account for a disproportionate share of all-time stolen funds, mostly from key compromise and verification bugs rather than clever math.

7.2 Core mechanics

Asset bridging patterns

  • Lock/mint: lock native asset on chain A, mint wrapped on chain B. Redeem by burning on B, unlocking on A. Wrapped asset is only as good as the lockbox.
  • Burn/mint (canonical, e.g., native issuance like CCTP for USDC): no lockbox; issuer-controlled.
  • Liquidity network (Hop, Across, Connext, Stargate): LPs hold inventory on both sides; relayers front liquidity; settlement/rebalancing later. Risks: LP accounting, fraud proofs on settlement, relayer griefing.
  • Intent-based (Across, UniswapX cross-chain): user signs intent; solvers fill; optimistic settlement with disputes.
  • Rollup canonical bridges: L1 escrow, L2 mint; withdrawals proven by fraud/validity proof (see Chapter 13).

Verification models (trust ladder, weakest to strongest) 1. Externally verified / multisig / MPC (Multichain, Ronin, Harmony, Orbit, early Wormhole guardians 13/19): trust m-of-n signers. 2. Optimistic (Nomad, Across, Hyperlane optimistic ISM): watchers can dispute during a challenge window; trust at least one honest watcher. 3. Light-client / on-chain verification (IBC, Rainbow Bridge, zk light clients like Succinct/Polyhedra/ Telepathy): trust the chain's consensus and the client implementation. 4. Native/rollup verification: inherit L1 security; limited by proof system and upgrade keys.

Message structure: (sourceChain, destChain, sender, nonce, payload); replay protection by nonce or message hash; domain separation to prevent cross-chain/cross-bridge replay.

Token mapping: registry of which wrapped token corresponds to which native; decimals normalization (wrapping 18-decimals to 8, dust).

7.3 Code anatomy (read order)
  1. A simple lock/mint bridge (write one yourself first, then audit it).
  2. Nomad Replica/Home (process, acceptableRoot, prove), UpdaterManager.
  3. Wormhole core Implementation/Messages (parseAndVerifyVM, guardian set update), token bridge Bridge, BridgeGetters; Solana side (Rust) post_vaa, signature verification via secp256k1 program and sysvar instructions.
  4. Ronin/Harmony-style multisig bridge: signature threshold checks, nonce handling, withdrawal limits.
  5. Across SpokePool/HubPool (fill proofs, relayer refunds, dispute).
  6. Axelar AxelarGateway, AxelarGasService; Circle CCTP TokenMessenger/MessageTransmitter.
  7. Rollup bridge: Optimism L1StandardBridge, OptimismPortal, L2OutputOracle/dispute games; Arbitrum Inbox/Outbox/Bridge.
7.4 Invariants
  • Conservation: locked_on_origin >= minted_on_destination (supply of wrapped ≤ escrow) at all times.
  • Each message is processed at most once; each withdrawal claimed at most once.
  • A message is only processed if provably emitted by the correct source contract on the correct chain.
  • Admin/guardian set updates cannot be done by non-quorum or replayed.
  • Rate limits and caps hold across all paths (including emergency/fallback).
  • Failed message handling does not lock funds permanently nor allow retry that double-spends.

8.1 Why it matters

Messaging layers are the plumbing used by hundreds of apps (OFT tokens, cross-chain lending, governance). The integrator's configuration is the most common failure point, not the protocol's core.

8.2 Core mechanics (know all of these)

9. Restakingorig #7

In plain English: Reusing staked ETH to secure other services, with extra ways to be slashed. Stacked trust means stacked failure paths, and one fault can spread widely.

Difficulty ●●●●●Time ~2 weeksNeeds: Ch 4, 5

Primary lenses: Trust & Power, Long-Term Evolution, Failure Modes, Assumptions.

9.1 Why it matters

Restaking stacks trust: ETH validator security is reused to secure other services (AVSs) with new slashing conditions, while liquid restaking tokens (LRTs) add another layer of operators, oracles and depeg risk. Correlated slashing is the systemic risk.

9.2 Core mechanics (EigenLayer; verify against latest release)
  • Restakers deposit LSTs (via StrategyManager strategies) or restake native ETH via EigenPods (validator withdrawal credentials pointed to a pod; beacon-state proofs verify balances/withdrawals).
  • Operators register, receive delegations; restakers delegate via DelegationManager.
  • AVSs (Actively Validated Services) define tasks, rewards, and slashing conditions; operators opt-in via AVSDirectory / Operator Sets + AllocationManager (unique stake allocation and slashing introduced by the slashing/redistribution upgrade).
  • Shares accounting: deposits mint shares in a strategy; delegation updates operator share totals; withdrawals are queued with a delay (escrow period; slashing during it must apply). Native restaking uses beaconChainETHStrategy shares that can be negative/adjusted on slashing/balance decreases.
  • Rewards: RewardsCoordinator distributes AVS rewards via merkle roots; claiming, earner/claimer roles.
  • Slashing: AVS slasher contract requests slash on operator set + strategies with magnitudes; slashing reduces allocated magnitude; shares are scaled by operator max magnitude and deposit scaling factor (design to make slashing O(1) and withdrawal-time aware).
  • LRTs (ether.fi, Renzo ezETH, Kelp rsETH, Puffer pufETH, Swell rswETH): pooled deposit → delegate to operators → LRT exchange rate by oracle (TVL across strategies) → withdrawal via queue. Symbiotic and Karak are alternative restaking systems (vault-based, different slashing models).
9.3 Code anatomy
  1. StrategyManager, StrategyBase (shares↔underlying), StrategyBaseTVLLimits.
  2. DelegationManager: delegateTo, queueWithdrawals, completeQueuedWithdrawal, share scaling with slashing.
  3. EigenPod / EigenPodManager: verifyWithdrawalCredentials, verifyBalanceUpdates, verifyCheckpointProofs, startCheckpoint, proofs against beacon state root (EIP-4788 oracle).
  4. AllocationManager: createOperatorSets, modifyAllocations, slashOperator, allocation delay.
  5. RewardsCoordinator: processClaim, merkle root submission, activationDelay.
  6. A LRT: deposit pool, rate oracle, withdrawal manager, operator delegator contracts, unstakingVault.
  7. Symbiotic Vault, Slasher, Burner, Delegator, resolver/veto flow.
9.4 Invariants
  • Total shares across all stakers ≥ sum of operator-delegated shares; delegation and undelegation conserve shares.
  • Underlying value of shares monotonically non-increasing only by slashing/loss events.
  • A slash during the withdrawal queue applies to queued withdrawals (no escape by queueing).
  • A slash cannot exceed an operator's allocated magnitude for that operator set.
  • Pod balance proofs cannot be replayed, reordered, or proven for the wrong validator/epoch.
  • LRT rate reflects realizable value; a depeg of any underlying LST/slashing is reflected before mints/redeems.
  • Rewards are claimable once, only by the rightful claimer; no double-claim across roots.

10. Account Abstractionorig #11

In plain English: Wallets that are programs. Security is entirely about how a wallet decides that a request is authorized, and who can change those rules.

Difficulty ●●●●○Time ~1 weekNeeds: Ch 1

Primary lenses: Trust & Power, Human Reality, Order & Control Flow.

10.1 Why it matters

Smart accounts hold user funds and run arbitrary validation logic. The attack surface is signature validation, module/plugin power, initialization, and the bundler/paymaster economic layer.

10.2 Core mechanics

ERC-4337 (no protocol change):

  • UserOperation: sender, nonce, initCode, callData, callGasLimit, verificationGasLimit, preVerificationGas, maxFeePerGas, maxPriorityFeePerGas, paymasterAndData, signature (v0.7+ uses packed fields).
  • Flow: user signs UserOp → bundler simulates and bundles into EntryPoint.handleOps → EntryPoint calls account.validateUserOp (validation phase), pays gas via account deposit or paymaster (validatePaymasterUserOp, postOp) → execution phase → refunds.
  • Validation rules (ERC-7562): limited opcodes (no TIMESTAMP, BLOCKHASH, etc. in validation), storage access restricted to the account's own storage/associated slots, staking for entities (factories, paymasters, aggregators) to defend the bundler mempool against DoS.
  • Nonce: 192-bit key + 64-bit sequence for parallel lanes.
  • Aggregators: signature aggregation (BLS) to save gas.

ERC-7579 / modular accounts: validators, executors, hooks, fallback handlers as modules; installModule / uninstallModule; module types and execution modes. Safe Safe7579 adapter, ZeroDev Kernel, Biconomy Nexus, Rhinestone modules.

EIP-7702 (Pectra, May 2025): an EOA signs an authorization to set code (a delegation designator 0xef0100 || address) so it behaves like a smart account. New risks: the EOA's private key still has full control (key = ultimate authority), phishing of authorizations, cross-chain authorization (chainId 0), storage collisions between delegates, tx.origin-based checks failing, extcodesize-based EOA detection, initialization front-running of delegate storage.

Others: Safe (multisig + modules + guards), Argent (guardians, recovery), passkeys (secp256r1/WebAuthn, RIP-7212 precompile), session keys, social recovery, ERC-1271 for signature validation, ERC-6900 (alternate modular standard).

10.3 Code anatomy
  1. EntryPoint (handleOps, _validatePrepayment, _executeUserOp, _postExecution, innerHandleOp, _getRequiredPrefund, deposit/stake accounting).
  2. A minimal SimpleAccount + SimpleAccountFactory.
  3. VerifyingPaymaster and a token paymaster.
  4. Safe Safe.sol (execTransaction, checkSignatures, module/guard execution, delegatecall operations) and the 4337 module.
  5. Kernel/Nexus validator and executor module architecture.
  6. A passkey validator (WebAuthn verification: authenticator data flags, challenge binding, clientDataJSON parsing).
  7. A 7702 delegate contract and initialize/execute design.
10.4 Invariants
  • Only the intended validator(s) can authorize actions; a UserOp cannot execute without passing the account's validation.
  • A signature is valid for one chain, one account, one nonce (no replay).
  • Installing or uninstalling modules requires authorization from existing owner/validator logic.
  • Paymaster only pays for ops satisfying its policy; it cannot be drained by gas griefing beyond its own limits.
  • Account initialization can happen only once and only by the intended party (factory + salt bound to owners).
  • Validation is deterministic across simulation and inclusion (no environment-dependent behavior).

11. MEVorig #12

In plain English: Block builders can reorder transactions. Assume a smart adversary sees your pending transaction and picks the most profitable order around it.

Difficulty ●●●○○Time ~1 weekNeeds: Ch 2

Primary lenses: Adversary Thinking, Order & Control Flow, Time.

11.1 Why it matters

MEV is the economic adversary model of Ethereum. Any function that is profitable to reorder, insert before, or insert after will be exploited by bots.

11.2 Core mechanics

The supply chain (post-Merge, MEV-Boost): users/searchers → mempool or private order flow (Flashbots Protect, MEV Blocker, builders' RPCs) → builders (construct blocks, bid) → relays → proposer (validator) picks the highest bid. ePBS (EIP-7732) is planned to enshrine this; verify status.

Strategies:

  • Arbitrage: cross-DEX price differences; atomic bundles.
  • Sandwich: front-run (buy), victim trade moves price, back-run (sell). Profit bounded by victim's slippage tolerance. Math: for V2 pool, optimal front-run size solves for max profit(dx) given victim's amountOutMin.
  • JIT liquidity: add liquidity right before a large swap, remove after; collects fees with low risk.
  • Liquidation: bots race to liquidate positions (priority gas auctions → now bundles/priority fees).
  • Back-running: oracle updates, governance actions, NFT mints.
  • Long-tail: time-bandit/reorg (mostly PoW), multi-block MEV (same builder/proposer controls consecutive slots), CEX-DEX arbitrage, NFT sniping, token launch sniping.
  • Order-flow protection/intents: CoW Protocol (batch auctions, uniform clearing price, solvers), UniswapX (Dutch auction fills), 1inch Fusion, private RPCs, MEV-Share (refunds to users), Flashbots Protect, MEV Blocker.
  • Protocol-level defenses: commit-reveal, batch auctions, encrypted mempools (threshold encryption, SUAVE-like ideas), frequent batch auctions, oracle-aware AMMs (am-AMM, Sorella/Angstrom), TWAMM.
11.3 What an auditor does with MEV

For every user-facing and keeper-facing function, ask: 1. Is there an observable pending transaction that signals profit? 2. Can an attacker insert before to change state/price and profit from the victim's tx? 3. Can an attacker insert after (back-run) to capture value from state change? 4. Does the function accept user-chosen slippage/deadline, and is it enforced against a safe reference, not the same manipulable pool? 5. Can the attacker choose when to trigger (e.g., harvest, rebalance, liquidate, oracle update)? 6. Are there public, permissionless keeper functions whose rewards are front-runnable (the keeper gets sniped)? 7. Does the protocol leak value to builders (priority fees, tips) and does an attacker-builder collusion change the threat model?

11.5 Invariants (design properties)
  • A user's execution price is within their stated slippage of a reference price that is not controlled by the same transaction.
  • Keeper incentives are sufficient for timely action but do not leak more value than necessary.
  • State-changing public functions cannot be profitably sandwiched beyond economic bound.
  • Commit-reveal or batch designs prevent information leakage before settlement.

12. Zero-Knowledge Proofsorig #10

In plain English: Proofs that a computation was done correctly without revealing inputs. The danger: a proof can verify even though the circuit forgot to enforce a rule.

Difficulty ●●●●●Time ~3 weeksNeeds: math comfort, Ch 1

Primary lenses: Assumptions, System Boundary, Trust & Power.

12.1 Why it matters

ZK systems fail in ways EVM auditors aren't used to: a circuit can be valid and still under-constrained, letting a prover forge a witness. Bugs are silent: proofs verify.

12.2 Core concepts
  • Statement/relation: prove knowledge of private w such that R(x, w) = true for public x. Properties: completeness, soundness, zero-knowledge.
  • SNARKs vs STARKs: Groth16/PLONK/Halo2 (succinct, trusted setup for Groth16 and universal setup for PLONK-KZG) vs STARKs/FRI (transparent, hash-based, larger proofs).
  • Arithmetization: R1CS (A·B=C constraints), PLONKish (gates + copy constraints + lookups), AIR (STARKs).
  • Circuit languages: Circom (R1CS), Noir (ACIR → Barretenberg/UltraHonk), Halo2 (Rust), Cairo (STARKs), Gnark, zkVMs (RISC Zero, SP1, Jolt) where Rust compiles to a proven VM.
  • Verifier contract: a Solidity contract performing pairing checks (bn254 precompiles 0x06, 0x07, 0x08) with fixed verification key and public inputs.
  • Applications: privacy (Tornado Cash, Semaphore, Aztec/Noir apps, Zcash-style shielded pools), zkRollups (zkSync Era, Starknet, Scroll, Linea, Polygon zkEVM), identity/ZK-KYC, ZK coprocessors, bridges (ZK light clients), voting (MACI).
12.3 Where bugs live (the taxonomy)
  1. Under-constrained circuits (the dominant class): a signal is assigned (<--) but not constrained (===), or constraint is too weak. Prover can choose arbitrary values.
  2. Over-constrained circuits: valid witnesses rejected, causing liveness failures or locking funds.
  3. Missing range checks / overflow in field arithmetic: field elements wrap modulo the prime; a < b needs bit-decomposition checks.
  4. Non-determinism misuse: hints/unconstrained functions (Noir unconstrained, Circom <--) must be verified by constraints.
  5. Public input binding errors: verifier accepts a proof but the contract doesn't bind public inputs to the real transaction data, so proof replayed or reused.
  6. Nullifier/commitment errors: nullifier not uniquely bound to the note; reuse enables double-spend; or leaks linkage.
  7. Fiat-Shamir flaws ("Frozen Heart", Trail of Bits 2022): not hashing all public inputs/commitments into the challenge → forged proofs.
  8. Trusted setup problems: toxic waste compromised, malformed setup, mismatched verification key (Zcash Sprout counterfeit flaw found 2018 was a parameter/construction issue; Tornado Cash had a ceremony).
  9. Verifier contract bugs: missing subgroup/curve checks, wrong field modulus, proof malleability, unchecked precompile return, public input not reduced < p.
  10. Cryptographic assumption misuse: weak hash for in-circuit use, unsafe randomness, too-small field choices.
  11. zkVM/zkEVM soundness bugs: missing opcode constraints, memory consistency, precompile/lookup gaps (found in many zkEVM audits).
  12. System-level: centralized prover/sequencer, upgrade keys, lack of forced-exit, DA assumptions, proof system version mismatch.

Under-constrained example (Circom):

// Intended: out = 1 if in == 0 else 0
template IsZeroBad() {
    signal input in;
    signal output out;
    signal inv;
    inv <-- in != 0 ? 1/in : 0;    // hint, unconstrained assignment
    out <-- -in*inv + 1;            // BUG: assigned, not constrained
    // Missing: out === -in*inv + 1;  and  in*out === 0;
}
// Correct version constrains both:
//   out <== -in*inv + 1;
//   in*out === 0;

A malicious prover sets out freely; any circuit using this as a check (e.g., "balance is zero") is forgeable.

12.4 Code anatomy
  1. circomlib basics (Num2Bits, LessThan, IsZero, Poseidon, MiMC), then audit a Semaphore or Tornado-style circuit.
  2. Generated Groth16 verifier contract (verifyProof): public input handling, pairing call.
  3. A zkRollup: ZkSync/Starknet/Scroll L1 contracts (commitBatches, proveBatches, executeBatches, verifier, priority queue, exit).
  4. Halo2/PLONK custom gate for a simple opcode; read an audit finding on a missing constraint.
  5. A zkVM guest/host (SP1/RISC Zero): what's proven vs what's public input.
  6. MACI or Aztec Noir contract: nullifiers, note trees, private/public state.
12.5 Invariants
  • For every output/signal: it is uniquely determined by constrained inputs (no free variables).
  • Range checks: every value used in comparison/arithmetic has bounds proven.
  • Every nullifier is unique per note and cannot be re-derived to collide.
  • The verifier checks proof against exact public inputs bound to on-chain state (root, nullifier hash, recipient, fee, chain).
  • L1 contract can't accept a state root without a valid proof; exit paths work even if sequencer censors.

13. Chains: L1, L2, and non-EVMorig #9

In plain English: The platform under everything. The same contract behaves differently on different chains: finality, gas, opcodes, sequencers. Know how users exit when things fail.

Difficulty ●●●●○Time ~2 weeksNeeds: Ch 1

Primary lenses: System Boundary, Failure Modes, Long-Term Evolution, Assumptions.

13.1 Why it matters

Contract behavior depends on chain facts: finality, gas semantics, opcodes, sequencer behavior, account model. "It works on mainnet" is not a spec for L2s or other VMs.

13.2 Core concepts

Ethereum L1: Gasper = LMD-GHOST fork choice + Casper FFG finality; slots 12s, epochs 32 slots; finality after ~2 epochs (about 13 minutes); reorgs possible before finality; MEV-Boost; Dencun blobs (EIP-4844); Pectra changes (EIP-7702, 7251, 7002).

Other consensus families: Tendermint/CometBFT (instant finality, validator set ≥ 2/3), Solana (Tower BFT + Proof of History, parallel runtime Sealevel, leader schedule, skipped slots), Avalanche, BNB Chain (Parlia), Polygon PoS, Bitcoin (PoW, probabilistic finality, 51% attacks).

L2s and rollups:

  • Optimistic: Optimism/OP Stack (Cannon fault proofs, dispute games), Arbitrum (BoLD, Nitro), Base, Blast; 7-day challenge window; sequencer ordering; forced inclusion via L1.
  • ZK rollups: zkSync Era, Starknet, Scroll, Linea, Polygon zkEVM; validity proofs; faster finality; prover and sequencer centralization.
  • Validiums/Optimiums: off-chain DA; DA committee/Celestia/EigenDA trust.
  • L2Beat stages: Stage 0 (training wheels full), Stage 1 (limited), Stage 2 (permissionless) frameworks to assess decentralization.
  • L1↔L2 messaging: retryable tickets (Arbitrum), CrossDomainMessenger (OP), alias addresses for L1→L2 callers (Arbitrum applies an offset to sender address), gas pricing with L1 data fee.

Solana model (non-EVM): accounts hold data, programs are stateless; accounts passed explicitly; PDAs; CPIs; rent; discriminators (Anchor); signer/owner checks are the programmer's job.

Move chains (Sui, Aptos): resource-oriented, linear types, objects, abilities (key/store/copy/drop); different bug classes (capability leaks, shared object contention, generic type confusion).

Cosmos SDK: modules, ABCI, keepers, x/bank, IBC; Go bugs: nondeterminism (map iteration, floats), panics in BeginBlock/EndBlock halting the chain, unbounded loops, rounding with sdk.Dec.

Appendix G. Glossary (quick)

  • AMM: automated market maker; price determined by a formula over reserves.
  • AVS: actively validated service secured by restaked assets.
  • Bad debt: debt not covered by collateral after liquidation.
  • CEI: checks-effects-interactions pattern.
  • CPI: cross-program invocation (Solana).
  • DVN: decentralized verifier network (LayerZero).
  • ERC-4626: tokenized vault standard.
  • Flash loan: uncollateralized loan repaid within the same transaction.
  • Health factor: ratio of risk-adjusted collateral to debt; <1 means liquidatable.
  • ISM: interchain security module (Hyperlane).
  • JIT liquidity: liquidity added just before a swap and removed after.
  • LRT/LST: liquid restaking / liquid staking token.
  • MEV: value extractable by ordering/inclusion of transactions.
  • Nullifier: unique value revealed to prevent double-spend of a private note.
  • OApp/OFT: LayerZero omnichain application / fungible token.
  • PDA: program derived address (Solana).
  • PBS: proposer-builder separation.
  • Sequencer: L2 node ordering transactions.
  • Slashing: penalty for provable misbehavior.
  • TWAP: time-weighted average price.
  • UserOperation: ERC-4337 transaction-like object.
  • VAA: verified action approval (Wormhole).
  • Witness: private input to a proof (circuit).
